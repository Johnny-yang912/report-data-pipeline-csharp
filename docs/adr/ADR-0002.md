# ADR-0002：缺 `ReportId` 視為身分失敗，由 Processor 標記；錯誤以 `ErrorCode` 分類，並透過 log 與 metrics 追蹤

| | |
|---|---|
| **狀態** | Accepted |
| **日期** | 2026-10-05 |
| **層** | 攝入 — 入口、Raw 狀態機、可觀測性 |

---

## 背景

ADR-0001 之後，入口不再解析 payload，`ReportId` 只在 Processor 解析一次。這留下一個問題：**缺 `ReportId` 的資料，要在哪裡、被當成什麼來處理？**

原本的處理方式有缺陷。`Cleaner` 把 `MISSING_REPORT_ID` 和其他必填欄位一起當成品質問題，資料照樣寫入 ODS，只標 `IsCleaned = false`；`ToReport` 再用 `?? string.Empty` 把 null 存成空字串。結果是：

1. 第一筆缺 ID 的資料以 `""` 寫入 ODS。
2. 之後每一筆缺 ID 的資料都撞上 `UNIQUE(ReportId)`，被標成 `duplicate`。

這些資料既不是重複，也沒有被「標記不拒絕」，而是被錯誤分類了。

做決策時有三個關鍵事實：

- **上游是機台或 MES 閘道。** 它們通常不會解讀 HTTP 回應碼，也不會依回應碼自動修正後重送。
- **缺 `ReportId` 是確定性錯誤，不是暫時性錯誤。** 常見原因是上游的欄位對應改了（例如 `reportId` 被改名成 `report_no`）、新機台設定錯誤，或上游程式有 bug。同一份 payload 重送幾次都一樣缺 ID。
- **系統原本無法辨識來源。** 唯一的來源線索是 payload 裡的 `MachineId`，而它和 `ReportId` 一樣是解析出來的業務欄位，欄位對應壞掉時可能一起缺失。

## 決策

### 1. 身分在 Processor 判定

Processor 依序經過三道關卡，每一道都建立在前一道通過的基礎上：

| 關卡 | 判斷什麼 | 失敗時 |
|---|---|---|
| 形狀 | payload 能否反序列化 | Raw 標 `error`，不寫 ODS |
| **身分** | `ReportId` 是否存在（null、空字串、全空白都算缺） | **Raw 標 `error` + `MISSING_REPORT_ID`，不寫 ODS** |
| 品質 | 其他必填、正規化、單列規則（`Cleaner`） | 寫入 ODS，標 `IsCleaned = false` |

**身分決定「能不能成為 ODS 的一列」，品質決定「這一列乾不乾淨」。** 只有品質問題適用「標記不拒絕」。

### 2. 來源身分取自傳輸層

入口以 `X-API-Key` 驗證上游，每個來源一把 key，透過對照表得到 `SourceClientId`，寫入 Raw。

- 來源取自傳輸層，**不經過 payload 解析**，因此與 ADR-0001「Raw 不混入解析出來的業務欄位」不衝突。
- `SourceClientId` 可為 NULL，代表「不是經由 API 寫入」（例如手動補資料）。
- 缺少或錯誤的 key 一律回 401，不寫入 Raw。

### 3. 錯誤以結構化 `ErrorCode` 分類

Raw 新增 `ErrorCode` 欄位，值來自固定清單（`ErrorCodes`）：

| ErrorCode | Raw 狀態 | 意義 | 重放有沒有用 |
|---|---|---|---|
| `JSON_PARSE_ERROR` | `error` | 語法正確，但結構或型別不符 | 需先修正（上游或我方對應規則）後重放 |
| `JSON_NULL_PAYLOAD` | `error` | payload 為 `null` | 需先修正（上游或我方對應規則）後重放 |
| `MISSING_REPORT_ID` | `error` | 沒有業務身分 | 需先修正（上游或我方對應規則）後重放 |
| `DUPLICATE_KEY` | `duplicate` | `ReportId` 已存在於 ODS | 視情況 |
| `SYSTEM_ERROR` | `error` | 系統本身出錯 | 有用 |

規則：**有 `ErrorMessage` 的列，一定有 `ErrorCode`。** 錯誤碼只放在 `ErrorCode`，`ErrorMessage` 只放給人看的細節，不再夾帶錯誤碼前綴。

### 4. 三層觀察鏈

| 層 | 回答什麼 | 內容 |
|---|---|---|
| Raw | 「發生了什麼」（永久保存） | `Status`、`ErrorCode`、`ErrorMessage`、`SourceClientId`、原文 `Payload` |
| log | 「哪一筆、為什麼」（單筆調查） | 結構化欄位 `RawId`、`ErrorCode`、`SourceClientId` |
| metrics | 「多少」（總量監控） | counter `reportpipeline.raw.outcomes`，標籤 `status`、`error_code`、`source` |

log 等級：

| 情況 | 等級 |
|---|---|
| 處理成功 | 不記（Worker 層以 Debug 記錄） |
| 資料錯誤、duplicate | Warning，不附 exception |
| 系統錯誤 | Error，附 exception，**在標記狀態之前記錄** |

## 理由

**① 在入口回 4xx 不會觸發重送。** 依 HTTP 慣例，4xx 代表「請求本身有錯，不要重試」。缺 ID 又是確定性錯誤，重送也沒用。所以入口拒絕唯一的價值，是**即時告訴送出的人**；但機台不讀回應碼，這個價值在正式運作時並不存在。

**② 所有失敗匯集成單一訊號。** 如果入口拒絕缺 ID 的資料，失敗就會分散在兩處：入口拒絕的在 log 和 HTTP 指標裡，Processor 判定的在 `raw.status` 裡。監控、告警和事後調查都要顧兩個來源。在 Processor 判定，所有失敗都進入同一個 `ErrorCode` 和同一個 counter。

**③ 保留完整證據。** 資料落地後，原文 `Payload` 一定保存在 Raw，而且保存期限由我們控制；log 則可能被輪替或抽樣。欄位被改名時，原文裡就看得到 `report_no` 這類線索，一眼就能看出原因。

**④ 依來源發現異常。** 有了傳輸層的 `SourceClientId`，「CNC-03 的 `MISSING_REPORT_ID` 突然暴增」就能直接從 metrics 看出來，並定位到是哪台機台出了問題。

**⑤ 用 `ErrorCode` 分類，而不是去解析訊息文字。** 訊息的語言和內容會隨環境改變。例如 SQL Server 會依照系統語言回傳中文的唯一鍵錯誤訊息。錯誤碼是固定的，可以安全地拿來分組和設告警。

## 後果

**上游拿不到即時回饋。** 缺 ID 的請求仍然回 202。串接期間，上游需要透過 `GET /api/reports/raw/{id}` 確認處理結果，或由我們從監控中發現問題後主動聯繫。

**不合法的資料會留在 Raw 裡，等待修正後重放。** 如果原因是上游改了欄位名稱，可以在解析前加入依來源的欄位對應，再重放受影響的 Raw，ODS 結構不需要改變；對應前必須先和上游確認語意相同。如果 payload 裡確實沒有身分資訊，則只能由上游補送。

**語法錯誤和結構錯誤的處理位置不同。** 端點參數是 `[FromBody] JsonElement`，框架在進到 Controller 之前就會先解析 JSON，語法錯誤的請求會直接回 400，不會寫入 Raw。能走到 Processor 的解析失敗，只剩「語法正確、但結構或型別不符」的資料。這個分界是框架的行為造成的，不是刻意設計，但結果是可以接受的：語法錯誤通常出現在串接初期，上游工程師這時會看回應碼。

**`Cleaner` 仍然保留 `MISSING_REPORT_ID` 檢查。** 經過 Processor 的資料不會觸發它，但 `Normalize` 會呼叫 `ReportId.Trim()`。保留這個檢查，`Cleaner` 才能獨立處理任何輸入，不會因為 null 而當掉，這和它「純函式、可獨立測試」的定位一致。

**系統錯誤會被記錄兩次。** Processor 的 catch 記錄後 `throw`，Worker 接住後再記錄一次。這違反「要嘛記錄、要嘛往外丟」的原則，但兩邊涵蓋的範圍不同：Worker 是最後一道防線，連 Processor 之外的錯誤（例如認領失敗）也接得到。

**關閉了部分框架 log（Development 環境）。** `Microsoft.EntityFrameworkCore.Update` 設為 `None`，否則每一筆 duplicate 都會先出現一條 EF Core 自己的 Error 和整段 stack trace，抵消掉 duplicate 只記 Warning 的設計。這樣做是安全的，因為每一個 `SaveChanges` 失敗都已經被我們的程式分級記錄。`Database.Command` 設為 `Warning`，避免 SQL 語句淹沒應用程式的 log。

**metrics 的標籤必須是有限集合。** `RawId`、`ReportId` 只放在 log，不當作標籤，以避免基數爆炸。

**catch 裡的計數必須寫明結果值。** catch 裡用 `ExecuteUpdateAsync` 直接修改資料庫，它不會更新記憶體裡被追蹤的 `Raw` 物件。此時物件上的 `Status` 仍是 `processed`，`ErrorCode` 仍是 null。所以 catch 裡傳給 metrics 的狀態和錯誤碼是直接寫明的，只有 `SourceClientId` 從物件讀取。

**Worker 的 `processed` Debug log 不精確。** 資料被標成 error 或 duplicate 時，`ProcessAsync` 是正常回傳，不會丟出例外，所以 Worker 判斷不出這筆失敗了。以 metrics 為準，因為 metrics 是在狀態確定的當下計數的。

**目前沒有告警，也沒有匯出 metrics。** 數據只能用 `dotnet-counters` 即時觀察。告警門檻需要依實際流量決定，匯出到外部監控系統不在這個系統的範圍內。

## 考慮過的替代方案

**在入口阻擋（回 400/422，不寫 Raw）。** 這是原作品的做法，優點是上游能拿到即時回饋。否決的理由是上述 ①～③：機台不讀回應碼、證據只剩 log、失敗訊號分散在兩處。ADR-0001 擔心的「兩邊解析不一致」，其實可以靠入口和 Processor 共用同一個反序列化函式解決，所以那**不是**否決的理由。

**寫入 Raw 並立即標 error，同時回 4xx。** 這個方案兼顧證據和回饋，但入口邏輯變重，而且上游每重送一次就多一筆 error。在上游不讀回應碼的前提下，回饋的那一半沒有價值。

**新增 Raw 狀態（例如 `invalid`）來區分「資料壞了」和「系統壞了」。** 這會擴張狀態機。`ErrorCode` 已經能做到這個區分，例如之後的重放端點可以依錯誤碼判斷重放是否有用。

**定期在資料表上執行 `COUNT ... GROUP BY Status` 來監控。** 成本會隨表變大而增加，要查時間窗還需要額外的索引。在狀態轉換當下計數，對資料庫的成本是零。

**所有上游共用一把 key。** 這樣驗證可以通過，但無法辨識來源，理由 ④ 就不成立了。

## 何時重新檢視

- **上游換成能解讀回應碼的軟體客戶端**，例如會依 4xx 自動修正的系統：重新評估「在入口阻擋」或「寫入並同時回 4xx」。
- **需要自動告警**：決定門檻，並接上 metrics 匯出。
- **Raw 的累積量開始影響儲存**：制定保存期限，但尚未處理完的 `error` 列不能在修正、重放之前被清除。

## 變更內容

- `ApiKeyMiddleware`、`ApiKeyEntry`：`X-API-Key` 驗證，以固定時間比對；key 對照表由設定讀取，未設定時啟動即失敗
- `RawModel.cs`：新增 `SourceClientId`（nvarchar(64)，nullable）、`ErrorCode`（nvarchar(64)，nullable）
- Migrations：`AddRawSourceClientId`、`AddRawErrorCode`
- `ErrorCodes`：錯誤碼常數清單
- `RawProcessor`：
  - 新增身分檢查關卡
  - `TryDeserialize` 分開傳回錯誤碼與訊息
  - 各錯誤路徑設定 `ErrorCode`
  - `ToReport` 移除 `ReportId ?? string.Empty`
  - 加入結構化 log 與 metrics 計數
- `PipelineMetrics`：counter `reportpipeline.raw.outcomes`
- `ChannelWorker`、`ScanWorker`、`Program.cs`：`Console.WriteLine` 改為 `ILogger`
- `appsettings.Development.json`：log 等級設定
