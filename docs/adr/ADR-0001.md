# ADR-0001：Raw 層移除 `ReportId`，以 `RawId` 追蹤到達、業務身分只存在 ODS

| | |
|---|---|
| **狀態** | Accepted |
| **日期** | 2026-10-01 |
| **層** | 攝入 — 儲存 |

---

## 背景

`Raw` 原本有一個從 payload 攤平出來的 `ReportId` 欄位，用途標註為「方便追蹤」。

實際檢查後發現兩個問題：

1. **這個欄位從來沒有被填過。** `PostRaw` 只寫入 `Payload`，`RawProcessor` 也沒有回寫，所以每一列都是 `string.Empty`。
2. **要填它，就得在入口解析 payload。** 這會帶來一致性問題：入口用 `JsonElement.TryGetProperty`（區分大小寫），Processor 用 `JsonSerializer` 搭配 Web 預設（不分大小寫）。如果上游送來 `{"reportId":"R001","ReportID":"R002"}`，兩邊可能各取到不同的值，造成 Raw 和 ODS 記錄的 ReportId 對不上。**錯誤的追蹤欄位，比沒有追蹤欄位更糟。**

因此真正的問題是：**Raw 層到底需不需要業務身分？**

## 決策

**移除 `Raw.ReportId`。** Raw 只保留原文（`Payload`）和處理狀態（`Status`、`ErrorMessage`、`ClaimedAt`）。

| 身分 | 欄位 | 代表什麼 | 重送時 |
|---|---|---|---|
| 物理身分 | `Raw.Id`（RawId） | **這一次到達** | 每次都產生新值 |
| 業務身分 | `Reports.ReportId` | **這個報工事件** | 重複，由唯一鍵擋下 |

**Raw 記錄到達，ODS 記錄事件。** 兩種身分各自屬於自己的層。

## 理由

**① 追蹤一次到達，靠的是 RawId。** Raw 的職責是「記錄到達了什麼」，而每一次到達的身分就是 RawId。用業務 ID 在 Raw 層追蹤，問的其實是「這個事件怎麼了」，這是 ODS 該回答的問題。

**② 一般的追蹤路徑已經存在。** `RawId會被一路帶往下游`，因此各層都能透過 RawId 走回原始到達。

**③ 少一個欄位，就少一個不一致的來源。** 業務欄位只在 Processor 用同一套反序列化規則解析一次，入口不再做第二次解析。

**④ Raw 回到純粹的記錄層。** 不混入任何「解析出來的」業務欄位，Raw 的內容就只會是「上游送了什麼」以及「系統處理到哪」。

## 後果

**有三種 Raw 沒有對應的 ODS 列，無法從 ODS 追回：**

| Raw 狀態 | 為什麼沒有 ODS 列 |
|---|---|
| `error` | 反序列化失敗，沒有產生 Report |
| `duplicate` | 寫入 Reports 時撞到唯一鍵，Report 沒有寫進去 |
| `pending` / `processing` | 還沒處理完 |

例如 R001 送了 3 次，會產生 RawId 1、2、3，但 ODS 只有一列，`RawId = 1`。只從 ODS 追，找不到 2 和 3。
**但重送本來就不是 ODS 該回答的問題。** 重送是「同一個事件到達了好幾次」，屬於到達層的異常，本來就該在 Raw 層檢查；ODS 只保留第一次成功的那筆，在設計上就看不到後面的重送。

**這類調查改用臨時查詢：**

```sql
SELECT Id, ReceivedAt, Status, ErrorMessage
FROM Raw
WHERE JSON_VALUE(Payload, '$.reportId') = 'R001';
```

這會全表掃描。**這是可以接受的成本**：查重送、查失敗件屬於偶發的調查，不是日常操作，不值得為它長期維護一個欄位和索引。

另外，`duplicate` 的 `ErrorMessage` 裡已經有 SQL Server 2627/2601 錯誤訊息帶出的重複鍵值，可以作為輔助線索，但它是文字、不是結構化欄位。

**如果之後「依業務 ID 查 Raw」變成經常性需求**（例如需要有索引的快速查詢），應該重新評估，並另寫一篇 ADR 取代本篇。

## 考慮過的替代方案

**在入口（`PostRaw`）解析並寫入 `ReportId`。** 可以讓 pending 和 error 的 Raw 也帶有業務 ID。否決的原因是背景提到的入口與 Processor 解析不一致。改用同一套反序列化設定可以解決一致性，但仍然是為了一個偶發需求，在 Raw 層長期維護一個業務欄位；而且要讓它可查詢，還需要把 `nvarchar(max)` 改成有長度的型別再加索引。

**在 Processor 反序列化成功後回寫 `ReportId`。** 解析規則一致，但 `error` 的 Raw 永遠不會有值，而失敗件正是最需要追蹤的。這個方案只對已經能從 ODS 追回的資料有效，等於沒有補到缺口。

**保留欄位但不填值。** 也就是原本的狀態。一個永遠是空字串的欄位會誤導讀者，否決。

## 變更內容

- `RawModel.cs`：移除 `ReportId` 屬性
- Migration `RemoveRawReportId`：`DropColumn("ReportId", "Raw")`
- `TryClaimRawTest`：seed 資料移除 `ReportId`
