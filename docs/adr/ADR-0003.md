# ADR-0003：DB 暫時性錯誤交由 EF Core 執行策略重試；重試的安全性由唯一鍵保證

| | |
|---|---|
| **狀態** | Accepted |
| **日期** | 2026-10-09 |
| **層** | 攝入 — 資料存取 |

## 背景

系統目前對資料庫錯誤沒有任何重試。只要遇到一次暫時性錯誤（連線中斷、逾時、DB 暫時無法連線），結果就依發生位置而不同：

| 發生位置 | 原本的結果 |
|---|---|
| `PostRaw` 寫入 Raw | 回 500，Raw 沒有寫入。上游是機台，不讀回應碼（見 ADR-0002），**這筆資料可能就此遺失** |
| `TryClaimRawAsync` 搶占 | 例外往外丟，Raw 仍是 `pending`，之後由 `ScanWorker` 撿回 |
| `ProcessAsync` 寫入 ODS | Raw 標 `error` + `SYSTEM_ERROR`，**要有人呼叫重試端點才會恢復** |

暫時性錯誤的特性是：**稍等幾秒再做一次，通常就會成功。** 為了這種錯誤遺失資料，或要求人工介入，代價都太高。

## 決策

**啟用 EF Core 內建的執行策略（Execution Strategy）**，讓暫時性錯誤在 EF Core 內部自動重試：

```csharp
options.UseSqlServer(connectionString, sql =>
    sql.EnableRetryOnFailure(
        maxRetryCount: 3,
        maxRetryDelay: TimeSpan.FromSeconds(5),
        errorNumbersToAdd: null));
```

- **只重試暫時性錯誤。** 哪些錯誤算暫時性，由 SQL Server provider 內建的錯誤碼清單決定。確定性錯誤（唯一鍵衝突 2627/2601、資料錯誤、我們自己丟的例外）不會重試。
- **重試的單位是一次 `SaveChanges` 或一次 `ExecuteUpdate`。** EF Core 會把每次 `SaveChanges` 包成一個交易，失敗時整個交易重做。`ProcessAsync` 第 5 步把「寫入 Report」和「Raw 標 processed」放在同一次 `SaveChanges`，所以重試時兩者仍然一起成功或一起失敗。
- **目前程式中沒有自行開啟的交易（`BeginTransaction`）。** 之後如果需要，必須用 `CreateExecutionStrategy().ExecuteAsync(...)` 包住整段交易，否則執行策略會直接丟出例外。

系統中的恢復機制分成三層，各自處理不同的問題：

| 機制 | 對象 | 時機 | 解決什麼 |
|---|---|---|---|
| EF Core 重試（本篇） | 單次 DB 操作 | 秒級，自動 | DB 或網路暫時不穩 |
| `ScanWorker` 回收 | 卡在 `processing` 的 Raw | 10 分鐘後，自動 | Worker 中途失敗 |
| 重試端點 | 已標 `error` / `duplicate` 的 Raw | 人工觸發 | 資料問題修正後重放、重試耗盡的系統錯誤 |

## 理由

**① 暫時性錯誤應該自己恢復。** 幾秒內就能解決的問題，不該變成遺失資料或待處理的 error。

**② 框架已內建，直接使用。** 自己寫重試是做得到的：原作品就是自己寫的，改用 Dapper 或 ADO.NET 自行管理連線時，寫法也和原作品相近。但 EF Core 已經內建這個機制，退避、隨機抖動、SQL Server 暫時性錯誤碼的判斷都處理好了。加上目前沒有自行開啟的交易，每個 DB 操作本身就是可以整個重做的單位，所以只要在 `Program.cs` 加一個設定，不需要改動既有程式碼。

**③ 重試的安全性由 DB 約束保證，不靠程式邏輯。** 重試最大的風險是重複寫入（見下一節）。`Reports` 上的 `UNIQUE(ReportId)` 和 `UNIQUE(RawId)` 保證 ODS 不會因為重試而出現重複資料。

## 後果

**commit 成功、但回應丟失時，重試會重做已經成功的操作。** 這種情況需要網路剛好在「DB 已 commit、回應尚未傳回」的幾毫秒內中斷，機率極低。各段程式的結果如下：

| 位置 | 重做後的結果 | ODS 是否正確 |
|---|---|---|
| `PostRaw` 寫入 Raw | Raw 表沒有唯一鍵，**多出一筆相同的 Raw**；往下處理時撞到 `ReportId` 唯一鍵，被標成 `duplicate` | 正確 |
| `TryClaimRawAsync` 搶占 | Raw 已不是 `pending`，更新 0 筆，被當成「已被搶走」而返回；Raw 停在 `processing`，**10 分鐘後由 `ScanWorker` 回收並重新處理** | 正確 |
| `ProcessAsync` 寫入 ODS | Report 撞到唯一鍵，進入 duplicate 的 catch；但 Raw 已經是 `processed`，條件 `Status == "processing"` 不成立，狀態不會被改。**metrics 會把這筆記成 `duplicate`，`processed` 少記一筆，並多一條 Warning log** | 正確 |

**已知限制：第三種情況的 metrics 誤記不處理。** 修正方式很簡單（依 `ExecuteUpdateAsync` 回傳的筆數判斷是否計數），但它只發生在極罕見的情況，ODS 資料也不受影響。解讀 `duplicate` 數量時要知道：其中可能有極少數其實是成功的資料。

**請求可能變慢。** DB 不穩時，`PostRaw` 會先在內部重試，最壞情況要等數十秒才回 500。在上游不讀回應碼的前提下，這比立刻失敗、遺失資料好。

**`SYSTEM_ERROR` 的意義變強。** 重試 3 次都失敗後，EF Core 丟出 `RetryLimitExceededException`，仍由原本的 `catch (Exception)` 標記為 `SYSTEM_ERROR`。這時它代表的不是「DB 抖了一下」，而是「DB 有一段時間無法使用」。

**重試次數沒有 metrics。** EF Core 每次重試都會寫一條 log（類別 `Microsoft.EntityFrameworkCore.Infrastructure`），目前的 log 設定不會過濾掉它。要調查網路或 DB 是否不穩，從 log 查。

**測試不涵蓋重試行為。** 測試使用 SQLite，不經過 `Program.cs` 的設定。重試由框架提供，本專案不另外測試它。

## 考慮過的替代方案

**自行撰寫重試（或使用 Polly）。** 原作品採用這種做法，在 C# 中改用 Dapper 或 ADO.NET 時也能以相近的方式實作。否決的原因不是做不到，而是 EF Core 已內建同樣的功能，自己寫等於重做一次框架已提供的東西。

**不在 DB 層重試，只依賴重試端點與 `ScanWorker`。** 這是原本的狀態。暫時性錯誤需要人工介入或等待 10 分鐘，而 `PostRaw` 失敗時資料根本不會進入系統，這兩個機制都救不回來。否決。

**修正 metrics 誤記。** 見「已知限制」。成本低，但只為極罕見的情況服務，暫不處理。

**新增重試次數的 metrics。** 可以繼承 `SqlServerRetryingExecutionStrategy` 並覆寫 `OnRetry()` 來計數，讓「DB／網路是否不穩」能從 metrics 直接看出來，並和 `duplicate` 對照，判斷問題出在哪一段。目前 log 已經足以調查，暫不處理。

## 何時重新檢視

- **改用雲端資料庫**（例如會做主備切換的服務）：暫時性錯誤會變多，「commit 成功但回應丟失」的機率也會上升。重新評估是否修正 metrics 誤記、是否新增重試次數 metrics。
- **需要針對 DB 不穩設告警**：新增重試次數 metrics。
- **程式中出現自行開啟的交易**：確認已用執行策略包住。

## 變更內容

- `Program.cs`：`UseSqlServer` 加上 `EnableRetryOnFailure`
